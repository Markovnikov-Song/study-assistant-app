# 功能文档编写规范

## 目标

每个用户能感知、能配置、会产生数据、会影响学习闭环或涉及平台权限的功能，都应该有文档。

文档分两类：

- Markdown：给人解释流程、边界、异常和验收。
- JSON：给 AI/程序定位功能、代码、API、数据模型和测试。

不是每个按钮都要单独写一篇文档，但每个完整功能单元都要能被未来开发者复原。

## Markdown 模板

```markdown
# 功能名称

## 基本信息

| 字段 | 内容 |
| --- | --- |
| 功能 ID | `module.feature` |
| 当前状态 | planned/prototype/partial/implemented/blocked/deprecated |
| 主要入口 | 路由或页面 |
| 后端前缀 | API 前缀 |
| 自动化覆盖 | 测试用例 |

## 功能目标

说明这个功能解决什么问题，在学习闭环中的位置是什么。

## 用户流程

1. 用户做什么。
2. 系统反馈什么。
3. 数据如何变化。

## 已实现能力

- 能力 1
- 能力 2

## 技术结构

| 层级 | 文件 | 说明 |
| --- | --- | --- |
| 页面 |  |  |
| Provider |  |  |
| Service |  |  |
| 模型 |  |  |
| 后端 |  |  |

## API 合同

列出核心端点、请求字段和响应概要。

## 数据与状态

列出本地状态、后端字段、缓存和任务队列。

## 行为边界

说明不能做什么、平台限制、失败降级和异常状态。

## 验证方式

列出自动化测试、手动测试和真机测试。
```

## JSON 规范

机器可读 JSON 放在 `docs/manifests/`。

| 文件 | 作用 |
| --- | --- |
| `features.json` | 功能状态、入口、平台、权限、缺口 |
| `code_map.json` | 功能到类、Provider、Service、后端、测试的映射 |
| `routes.json` | Flutter 路由和页面 |
| `apis.json` | API 合同概要和测试覆盖 |
| `data_models.json` | 数据表、Dart 模型和关键字段 |
| `test_matrix.json` | 测试层级、测试文件和通过状态 |

## 状态定义

| 状态 | 含义 |
| --- | --- |
| `planned` | 已规划，未实现 |
| `prototype` | 有 UI 或 demo，但未接真实数据 |
| `partial` | 部分可用，还有关键缺口 |
| `implemented` | 主流程已实现并有测试或合同支撑 |
| `blocked` | 受平台、权限、政策或依赖限制 |
| `deprecated` | 已废弃 |

## 编写原则

- 先写用户流程，再写技术实现。
- 明确已实现和未实现。
- 平台限制必须写清楚，尤其是 Android/iOS 权限。
- 文件路径必须指向真实文件。
- 自动化测试要写到文档里。
- JSON 不替代 Markdown；Markdown 不替代 JSON。
- 大功能完成后，同步更新 `docs/manifests/*.json`。
